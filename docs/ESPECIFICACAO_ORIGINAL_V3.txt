PROMPT MESTRE — FIXFLOWOS

1. OBJETIVO DO PROJETO

Criar um SaaS completo chamado FixFlowOS, destinado à gestão de lojas de
assistência técnica de celulares, tablets e outros dispositivos
eletrônicos.

O sistema deve ser moderno, profissional, responsivo e prioritariamente
desenvolvido para uso em:

-   celular;
-   tablet;
-   desktop.

A experiência mobile deve ser tratada como prioridade, pois técnicos e
vendedores utilizarão o sistema diretamente no balcão e na área técnica.

O nome oficial do sistema é exclusivamente:

FixFlowOS

Nunca utilizar “FixFlow Pro”, “FixFlowOS Pro” ou qualquer outra
variação.

------------------------------------------------------------------------

1. STACK OBRIGATÓRIA

Utilizar:

-   React;
-   Vite;
-   JavaScript;
-   Tailwind CSS;
-   Lucide React;
-   React Router;
-   Firebase Authentication;
-   Firebase Firestore;
-   Firebase Storage quando necessário;
-   Firebase Admin SDK no backend;
-   API Routes compatíveis com Vercel;
-   Vercel para deploy.

Evitar dependências desnecessárias.

A arquitetura deve ser organizada para facilitar manutenção, expansão e
correção de bugs.

------------------------------------------------------------------------

2. ARQUITETURA

O sistema deve ser multi-tenant.

Cada loja deve possuir isolamento completo dos seus dados.

Estrutura conceitual:

-   Super Admin;
-   Lojas;
-   Usuários;
-   Clientes;
-   Aparelhos;
-   Ordens de Serviço;
-   Estoque;
-   Produtos;
-   Vendas;
-   Caixa;
-   Financeiro;
-   Equipe/RH;
-   Assinatura/plano.

Nenhum usuário de uma loja pode acessar dados de outra loja.

Toda consulta e gravação de dados deve respeitar o tenantId/storeId da
loja do usuário autenticado.

------------------------------------------------------------------------

3. AUTENTICAÇÃO

Utilizar Firebase Authentication.

Método principal:

-   Email e senha.

Não criar sistema próprio de armazenamento de senhas.

Nunca armazenar senhas em texto puro no Firestore.

Regra de senha

A senha deve possuir uma regra baseada somente nos números de 1 a 9.

Exemplo de caracteres permitidos:

1234567890

O sistema deve validar essa regra durante criação/alteração de senha
quando aplicável.

------------------------------------------------------------------------

4. SUPER ADMIN

REGRA FUNDAMENTAL

O Super Admin NÃO deve possuir cadastro público dentro do sistema.

Não criar:

-   tela “Criar Super Admin”;
-   botão “Cadastrar Super Admin”;
-   formulário público para Super Admin;
-   criação automática de Super Admin;
-   script obrigatório de provisionamento;
-   criação do Super Admin durante o primeiro acesso;
-   criação do Super Admin pela interface normal.

O Super Admin deve ser criado exclusivamente pelo Firebase.

O administrador do projeto deverá:

1.  acessar o Firebase Console;
2.  acessar Firebase Authentication;
3.  criar manualmente o usuário com email e senha;
4.  utilizar o email autorizado para o Super Admin;
5.  atribuir a autorização necessária no backend/Firestore para
    reconhecer esse usuário como Super Admin.

O aplicativo apenas verifica a autorização do usuário autenticado.

Nunca permitir que um usuário comum consiga transformar a própria conta
em Super Admin.

Nunca confiar apenas em dados enviados pelo frontend para determinar se
alguém é Super Admin.

A autorização deve ser validada no backend e nas regras de segurança.

FINANCEIRO DA PLATAFORMA — SUPER ADMIN

Criar no painel /super-admin um dashboard financeiro exclusivo do
proprietário/administrador global da plataforma FixFlowOS. Esse painel
controla as receitas e os custos do negócio SaaS, não os caixas ou as
despesas operacionais das lojas clientes.

O dashboard deve ter design profissional e bonito, com cartões de
indicadores, gráficos legíveis, filtros de data e navegação simples.
Usar dados reais persistidos no Firestore e não valores fictícios em
produção.

Indicadores principais

-   faturamento total no período selecionado;
-   valores efetivamente recebidos;
-   valores previstos a receber;
-   valores vencidos e ainda não recebidos;
-   despesas pagas;
-   despesas previstas ou pendentes;
-   resultado/lucro estimado do período (receitas efetivas menos
    custos/despesas efetivamente pagos, deixando explícita a
    metodologia);
-   receita recorrente de assinaturas, quando houver dados suficientes;
-   quantidade de assinaturas ativas, vencidas e em período de teste.

Filtros e consultas

Permitir selecionar: - hoje; - últimos 7 dias; - mês atual; - mês
anterior; - ano atual; - intervalo personalizado com data inicial e
final.

Permitir consultar quanto está previsto para receber em uma data
específica ou em um intervalo de datas. A previsão deve ser baseada em
cobranças, vencimentos e assinaturas registradas no sistema. Diferenciar
visualmente previsão, valores vencidos, valores recebidos e valores
efetivamente pagos. Não considerar uma cobrança prevista como dinheiro
recebido.

Cadastro de custos e despesas da plataforma

Permitir ao Super Admin cadastrar, editar e consultar custos do negócio,
com: - descrição; - categoria; - valor; - data de competência; -
vencimento; - data de pagamento; - status (pendente, pago, vencido ou
cancelado); - recorrência (não recorrente, semanal, mensal, anual ou
outra periodicidade suportada); - observações; - vínculo opcional com
fornecedor ou serviço.

Exemplos de categorias: hospedagem, Firebase, domínio, ferramentas,
marketing, taxas, serviços terceirizados e outros custos operacionais.
Custos recorrentes devem gerar ocorrências futuras de forma controlada,
sem duplicações acidentais.

Regras financeiras

-   Manter receitas, cobranças, despesas e pagamentos em registros
    distintos, com identificadores e datas.
-   Permitir registrar manualmente o recebimento ou pagamento quando não
    existir integração de pagamento.
-   Não afirmar que houve recebimento real sem um registro confirmado.
-   Não inventar previsões nem assumir que todas as assinaturas serão
    pagas.
-   Exibir claramente os critérios utilizados nos cálculos.
-   Permitir abrir os detalhes que compõem cada indicador e exportar
    relatórios financeiros.
-   Permitir anexar comprovantes aos custos/despesas, com acesso
    protegido e armazenamento seguro.
-   Permitir filtros por data, categoria, recorrência, status e tipo.
-   Permitir previsões por data/período baseadas em cobranças,
    vencimentos e assinaturas registradas, distinguindo previsto,
    vencido e efetivamente recebido.
-   Permitir cenários de previsão para meses futuros, claramente
    identificados como estimativas, nunca como valores recebidos.
-   Não misturar custos e receitas da plataforma com os dados
    financeiros de qualquer loja.
-   Restringir esse painel exclusivamente ao Super Admin autorizado, com
    verificação no backend.
-   Registrar alterações e exclusões financeiras no histórico de
    auditoria.
-   Preparar a arquitetura para uma futura integração com gateway de
    pagamento, sem simular uma integração que não exista.

7. PERFIS DE USUÁRIO E PERMISSÕES

Criar cinco níveis claramente separados: SUPER ADMIN, ADMIN, GERENTE,
VENDEDOR e TÉCNICO.

SUPER ADMIN
Administrador global da plataforma FixFlowOS. Acessa /super-admin,
administra lojas, planos, assinaturas e o financeiro da plataforma.
Não é um usuário de loja e não deve misturar custos/receitas do SaaS com
o financeiro das lojas clientes.

ADMIN
Administrador de uma loja específica. Possui acesso amplo aos módulos
da própria loja, incluindo usuários, estoque, financeiro, caixa,
configurações, indicadores, OS, clientes, vendas e relatórios. Pode
consultar o histórico de auditoria da própria loja e analisar o
desempenho da equipe. Não pode acessar dados de outras lojas nem
conceder o papel de Super Admin.

GERENTE
Perfil de gestão operacional dentro de uma loja. Pode cadastrar e editar
produtos, registrar entradas, saídas e ajustes de estoque, consultar
custos e preços, visualizar alertas de estoque baixo, gerenciar vendas,
consultar relatórios operacionais, atribuir técnicos às OS e acompanhar
os consertos. Pode editar todos os campos das OS, incluindo
cliente/aparelho, diagnóstico, serviços, peças, técnico responsável,
orçamento, desconto, valores, pagamentos, status, datas e observações.
Pode consultar o histórico de auditoria e indicadores operacionais da
própria loja. Não recebe automaticamente permissão para administrar
configurações críticas, usuários/permissões, assinaturas da plataforma
ou dados de outras lojas. A gestão financeira administrativa da loja
permanece sujeita às permissões do Admin. Nunca pode se tornar Super
Admin.

VENDEDOR
Usuário operacional de atendimento e vendas. Pode cadastrar clientes,
abrir e editar OS, realizar vendas conforme as permissões da loja,
consultar produtos e estoque e visualizar as informações necessárias ao
atendimento. Pode consultar o histórico de auditoria da própria loja.
Não pode administrar configurações globais da loja.

TÉCNICO
Usuário focado na operação técnica. Pode visualizar, criar e editar OS,
atualizar etapas técnicas, adicionar diagnóstico, observações e serviços
executados, consultar produtos e disponibilidade do estoque. Não pode
cadastrar, excluir ou editar produtos, movimentar ou ajustar estoque
manualmente, criar categorias ou administrar o módulo de estoque.

REGRA DE EDIÇÃO DE ORDENS DE SERVIÇO
Todos os perfis de usuário da loja — Admin, Gerente, Vendedor e Técnico
— podem editar uma OS. Toda criação, edição, mudança de status,
alteração de valor, pagamento, atribuição ou cancelamento deve gerar
evento no histórico com usuário, papel, data/hora e detalhes da
alteração.

Não exigir que vendedor ou técnico preencha manualmente, como condição
obrigatória para salvar ou atualizar uma OS, cada insumo/consumível
utilizado. O registro de peças/insumos vinculados à OS pode ser opcional
ou seguir um fluxo de estoque definido pela loja, sem bloquear o
diagnóstico ou o andamento do conserto.

REGRAS GERAIS
- Aplicar permissões na interface, backend e regras do Firestore.
- Ocultar botões não substitui validação de autorização no backend.
- Todos os usuários autorizados da loja podem consultar o histórico da
  própria loja para saber quem realizou ações e o que foi alterado.
- Toda venda, OS, movimentação de estoque e ação financeira deve
  registrar o usuário responsável.
- Nenhum Admin, Gerente, Vendedor ou Técnico pode conceder a si mesmo
  privilégios superiores.
- Validar permissões explicitamente em cada operação.

13. ESTOQUE

Criar módulo de estoque completo, simples de operar e responsivo.

Recursos: - cadastro e edição de produtos; - categorias; - código de
barras; - custo unitário; - preço de venda; - quantidade atual; -
estoque mínimo; - fornecedor; - localização; - histórico de
movimentações; - alertas de estoque baixo.

Registrar movimentações: - entrada; - saída; - ajuste; - devolução; -
consumo de peças em OS.

Sempre registrar a data, o usuário responsável, a quantidade anterior e
posterior, a justificativa quando aplicável e a origem da movimentação.
Não permitir quantidades negativas sem uma regra explícita e autorizada.

Permissões

-   Admin: pode cadastrar, editar, excluir quando seguro, movimentar e
    configurar estoque.
-   Gerente: pode cadastrar e editar produtos, registrar entradas,
    saídas e ajustes, consultar custos e preços e acompanhar alertas de
    estoque baixo.
-   Vendedor: consulta produtos e disponibilidade; movimentações somente
    se houver permissão explicitamente concedida.
-   Técnico: consulta produtos e disponibilidade. O consumo de peça em
    uma OS deve seguir o fluxo autorizado e registrar a movimentação
    vinculada à OS, sem dar ao Técnico acesso à administração geral do
    estoque.

Exclusões de produtos com histórico devem ser evitadas; preferir
desativar/arquivar para preservar integridade dos relatórios e
movimentações.

14. VENDAS / PDV

Criar módulo de vendas (PDV) funcional.

Permitir:
- adicionar produtos e serviços;
- selecionar cliente quando aplicável;
- aplicar desconto conforme permissão;
- escolher método de pagamento;
- finalizar venda;
- registrar devoluções, trocas e observações, incluindo eventual
  diferença de dinheiro ou item devolvido;
- consultar histórico e detalhes da venda.

Métodos de pagamento configuráveis:
- dinheiro;
- PIX;
- cartão;
- outros;
- troca, com campo de observação para registrar devolução de dinheiro,
  item ou diferença envolvida.

ATRIBUIÇÃO E RELATÓRIOS DE VENDAS
Toda venda deve registrar de forma persistente o usuário que realizou a
operação, data/hora, itens, quantidades, preços, descontos, método de
pagamento, total, status e eventuais cancelamentos/devoluções. Salvar o
responsável no momento da operação; não inferi-lo posteriormente pelo
usuário atualmente conectado.

O Admin da loja deve consultar relatórios e filtros por período,
funcionário, produto, categoria e status, incluindo:
- quem vendeu mais;
- quantidade e valor das vendas por funcionário;
- quais produtos/serviços cada funcionário vendeu;
- produtos e serviços mais vendidos;
- faturamento bruto, descontos, devoluções e total líquido;
- histórico detalhado de cada venda;
- cancelamentos, trocas e devoluções, com responsável e justificativa.

O Gerente pode consultar relatórios operacionais de vendas conforme as
permissões da loja. Usar dados reais e respeitar o isolamento
multi-tenant. Nunca atribuir vendas a um funcionário sem registro.

18. ASSINATURAS, PLANOS E PREÇOS

O sistema deve possuir estrutura real para planos SaaS. Cada loja pode
possuir plano, status, período de teste, data de início, data de
vencimento, limites, recursos liberados e histórico de alterações.

O Super Admin deve poder criar, editar, ativar e desativar planos;
definir limites e recursos; alterar o preço de qualquer plano sempre que
desejar; criar preços promocionais e descontos temporários; definir
vigência inicial/final da promoção; e consultar lojas, status, testes e
vencimentos associados a cada plano.

ALTERAÇÕES DE PREÇO
Registrar quem alterou o preço, valor anterior, valor novo, data/hora,
vigência e motivo opcional. Permitir definir se a mudança vale apenas
para novas assinaturas ou também para renovações futuras. Alterações
não podem modificar silenciosamente cobranças já pagas nem apagar o
histórico. Mostrar claramente o preço e as condições aplicáveis a cada
loja/assinatura.

O painel deve distinguir valor contratado, valor previsto, valor
vencido e valor efetivamente recebido. Não afirmar que um pagamento
ocorreu sem confirmação registrada ou retorno de uma integração real.
Nenhum usuário de loja pode alterar preços globais ou dados de
assinaturas de outras lojas.

19. HISTÓRICO DE AUDITORIA E ATIVIDADES DA LOJA

Implementar histórico de auditoria pesquisável, acessível a todos os
usuários autorizados de uma loja. Cada usuário deve conseguir consultar,
na própria loja, quem fez o quê e quando. O histórico não pode permitir
acesso a dados de outra loja.

Registrar, quando aplicável:
- usuário responsável e papel no momento da ação;
- loja/tenant associado;
- tipo de ação: criação, edição, cancelamento, aprovação, mudança de
  status, pagamento, devolução etc.;
- entidade afetada (OS, produto, venda, cliente, despesa, receita,
  usuário etc.) e identificador;
- data/hora;
- campos alterados e valores anteriores/posteriores quando aplicável;
- justificativa para cancelamentos, ajustes ou ações críticas.

Registrar no mínimo alterações de OS; criação/edição/cancelamento de
vendas; descontos, trocas e devoluções; movimentações e ajustes de
estoque; alterações de preços e custos; pagamentos e mudanças
financeiras; alterações de papéis/permissões; mudanças de configurações;
e mudanças de planos, assinaturas e preços realizadas pelo Super Admin.

Oferecer busca e filtros por data, usuário, tipo de ação e registro. O
